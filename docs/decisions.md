### 태그 기반 예외 처리와 그 허점

**배경**

퍼블릭 액세스가 열린 버킷을 자동으로 차단하는 기능을 만들면서, 의도적으로 공개해야
하는 버킷을 어떻게 구분할지 정해야 했다. 정적 웹사이트 호스팅이나 공개 배포용
버킷처럼 퍼블릭 설정이 정상인 경우가 있기 때문이다.

구분 수단이 없으면 자동화가 정상 서비스를 중단시킨다. 반대로 너무 느슨한 예외를
만들면 자동화가 무력해진다.

**검토한 선택지**

| 방식 | 장점 | 단점 |
|---|---|---|
| 예외 목록을 코드에 하드코딩 | 변경 이력이 코드에 남음 | 버킷 추가마다 배포 필요, 소유자가 직접 못 함 |
| 별도 설정 파일/DB | 코드 변경 없이 관리 | 설정 저장소를 따로 운영해야 함 |
| 리소스 태그 | 소유자가 직접 부여, 별도 저장소 불필요 | 태그 부여 권한만 있으면 예외 처리 가능 |

**결정**

`AllowPublic=true` 태그가 부여된 버킷은 조치 대상에서 제외한다.

버킷 소유자가 자기 책임으로 태그를 부여하고, 자동화 코드는 그것을 신뢰하는 구조다.
예외의 근거가 리소스 자체에 붙어 있어 별도 조회 없이 판단할 수 있고, 자동화 코드를
수정하지 않고도 예외를 관리할 수 있다.

**허점**

이 구조는 **태그를 부여할 수 있는 사람이면 누구나 자동 조치를 무력화할 수 있다**는
전제 위에 있다. 실수로 태그를 잘못 붙이거나, 권한이 과도하게 부여된 사용자가
의도적으로 태그를 달면 위험한 버킷이 그대로 남는다.

즉 자동화의 실효성이 **태그 부여 권한의 관리 수준에 종속된다.**

**그럼에도 선택한 이유**

이 허점은 태그 방식만의 문제가 아니다. 어떤 예외 처리 방식이든 "예외를 등록할 수
있는 주체"가 있고, 그 주체의 권한 관리가 무너지면 같은 결과가 된다. 하드코딩
방식도 코드 저장소에 대한 쓰기 권한이 통제되지 않으면 마찬가지다.

문제를 없앨 수 없다면 **어디에 위치시킬지**를 선택하는 문제가 된다. 태그 방식은
그 지점을 IAM 권한 관리라는 이미 존재하는 통제 영역으로 옮긴다.

**보완 방향**

- **태그 변경 이력 감사** — `PutBucketTagging` API 호출을 CloudTrail에서 추적해,
  누가 언제 예외를 부여했는지 기록으로 남긴다. 이 프로젝트의 알림 시스템이 이미
  `PutBucketPublicAccessBlock`을 감시하고 있으므로 동일한 구조로 확장 가능하다.
- **태그 부여 권한 분리** — 버킷 생성 권한과 `AllowPublic` 태그 부여 권한을 분리하고,
  후자는 별도 승인을 거치도록 한다.
- **만료 시간** — 태그에 만료일을 함께 기록해, 기간이 지난 예외는 자동으로 무효화한다.
  임시로 열어둔 버킷이 영구 예외가 되는 것을 막는다.

**재검토 조건**

- 태그 부여 권한을 세밀하게 통제할 수 없는 조직이라면, 예외 목록을 코드나 별도
  승인 절차가 있는 저장소로 옮기는 편이 안전하다.
- 규제 준수가 요구되는 환경에서는 예외 자체를 허용하지 않고, 퍼블릭이 필요한
  경우 CloudFront 등 다른 경로를 강제하는 방식이 적절하다.

  ### 조치 엔드포인트를 POST로 전환

**배경**

초기 구현에서는 모든 엔드포인트를 GET으로 만들었다. 브라우저 주소창에 URL을 입력하면
바로 확인할 수 있어 개발 중 테스트가 편했기 때문이다.

그러나 `/remediate`와 `/auto-remediate`는 조회가 아니라 **S3 설정을 실제로 변경하는
작업**이다. 조회와 같은 방식으로 노출하는 것이 적절한지 다시 검토했다.

**문제**

HTTP 규약상 GET은 안전(safe)해야 한다. 서버 상태를 변경하지 않는다는 전제가 있고,
그 전제 위에서 여러 계층이 동작한다.

| 문제 | 내용 |
|---|---|
| 프리페치·캐싱 | 브라우저나 프록시가 링크를 미리 요청할 수 있다 |
| URL 노출 | `?dry_run=false` 같은 파라미터가 액세스 로그, 프록시 로그, 브라우저 히스토리, Referer 헤더에 남는다 |
| 재실행 용이성 | URL만 복사하면 누구나 다시 실행할 수 있고, 북마크로도 남는다 |
| 의미 전달 | 엔드포인트 목록만 봐서는 어느 것이 상태를 바꾸는지 알 수 없다 |

특히 두 번째가 문제였다. `dry_run=false`는 실제 변경을 일으키는 값인데, 그 값이 URL에
포함되면 로그를 보는 사람이나 히스토리를 뒤지는 사람이 그대로 재실행할 수 있다.

**결정**

조치 엔드포인트를 POST로 전환하고, 파라미터를 쿼리 스트링이 아닌 **요청 본문**으로
받도록 했다.

| 엔드포인트 | 메서드 | 파라미터 위치 |
|---|---|---|
| `/s3-status`, `/trail-history`, `/iam-status` | GET | 쿼리 |
| `/remediate`, `/auto-remediate` | POST | 본문 |

FastAPI는 `str`, `bool` 같은 단순 타입 파라미터를 기본적으로 쿼리 파라미터로 해석한다.
메서드만 POST로 바꾸면 값은 여전히 URL에 남으므로, Pydantic 모델로 정의해 본문에서
읽도록 했다.

```python
class RemediateRequest(BaseModel):
    bucket_name: str
    dry_run: bool = True
```

두 엔드포인트가 필요로 하는 입력이 다르므로 모델도 분리했다. `/auto-remediate`는
대상을 점검 결과에서 도출하므로 `bucket_name`을 받지 않는다. 모델을 공유하면
클라이언트가 사용되지 않는 값을 억지로 채워야 한다.

**부수 효과**

Swagger UI에서 GET은 파란색, POST는 초록색으로 표시된다. 엔드포인트 목록만 봐도
**조회와 변경이 구분**된다. 문서를 따로 작성하지 않아도 의도가 드러난다.

**트레이드오프**

브라우저 주소창으로 바로 호출할 수 없게 되어 수동 테스트가 번거로워졌다.
`curl`에 `-X POST`와 `Content-Type` 헤더를 명시해야 하고, 헤더를 빠뜨리면 422를 받는다.

개발 편의보다 실행 경로의 명확성을 우선했다. 조치는 자주 호출하는 기능이 아니고,
Swagger UI에서 테스트할 수 있으므로 실질적인 불편은 크지 않다.

**남은 원칙**

편의를 위해 선택한 구현이 나중에 위험 요소가 되는 경우가 있다. 초기에는 "테스트하기
편의를 위해" GET을 썼지만, 반대로 말하자면 누구나 URL로 실행할 수 있다와 같은 의미였다.

**재검토 조건**

- 현재는 인증 계층이 없어 POST로 바꿔도 호출 자체를 제한하지는 못한다.
  운영 환경이라면 API Key나 IAM 기반 인증이 선행되어야 한다.
- 조치 결과를 조회하는 엔드포인트가 필요해지면 `GET /remediate/{id}` 형태로
  분리해 실행과 조회를 명확히 나눈다.

### dry-run을 기본값으로

**배경**

점검 후 조치까지 자동화하기로 하면서, 잘못된 호출이 실제 변경으로
이어지는 것을 어떻게 막을지 정해야 했다.

이 프로젝트의 조치는 되돌리기 어렵지 않다(차단을 다시 풀면 된다). 그러나 대상이
계정의 모든 버킷이고, 한 번의 호출로 여러 리소스가 동시에 바뀐다. 의도하지 않은
실행의 영향 범위가 넓다.

**검토한 선택지**

| 방식 | 동작 | 위험 |
|---|---|---|
| 즉시 실행 | 호출하면 바로 조치 | 실수 한 번이 전체 버킷에 반영됨 |
| 확인 절차 | 실행 전 별도 확인 요청 | API에서는 세션 상태 관리가 필요 |
| dry-run 기본값 | 명시적으로 꺼야만 실제 실행 | 기본 동작이 무해함 |

**결정**

`dry_run` 파라미터의 기본값을 `True`로 두고, 실제 변경은 `dry_run=false`를 명시적으로
전달해야만 실행되도록 했다.

파라미터를 생략하거나 잘못 호출하면 아무것도 바뀌지 않는다. **위험한 동작을 하려면
의도를 표현해야 하고, 아무것도 표현하지 않으면 안전한 쪽으로 동작한다.**
"safe default" 패턴이다.

**dry-run이 무엇을 반환해야 하는가**

초기 구현에서는 dry-run 검사를 함수 맨 앞에 두었다. 실행을 막는 것이 목적이라고
보았기 때문이다.

```python
if req.dry_run:
    return {"status": f"dry-run 여부 - {req.dry_run}"}

if is_exempted(req.bucket_name):
    return {"status": "AllowPublic=true로 인해 제외됨"}
```

이 구조에서는 dry-run 응답이 항상 같은 문자열이었다. 태그 예외 검사에 도달하지
않으므로, **실행하면 무슨 일이 일어나는지 알 수 없다.**

dry-run의 목적은 실행을 막는 것이 아니라 **결과를 미리 보여주는 것**이다.
`terraform plan`이 그렇듯, 변경 전에 무엇이 바뀔지 확인할 수 있어야 의미가 있다.

검사 순서를 바꿔 태그 예외를 먼저 판정하도록 했다.

```python
if is_exempted(req.bucket_name):
    return {"status": "AllowPublic=true로 인해 제외됨"}

if req.dry_run:
    return {"status": "[dry-run] 퍼블릭 액세스 차단을 적용할 예정"}
```

이제 dry-run 결과에서 "태그로 제외될 버킷"과 "조치가 적용될 버킷"이 구분된다.
`/auto-remediate`로 여러 버킷을 훑을 때 특히 유용하다.

**검증**

두 안전장치가 서로 독립적으로 동작하는지 확인했다. `dry_run=false`로 실제 조치를
요청했을 때도 태그가 있는 버킷은 제외된다. 하나가 통과해도 다른 하나가 막는다.

**트레이드오프**

기본값이 안전한 대신, 실제 조치를 하려면 매번 `dry_run=false`를 명시해야 한다.
운영에서 반복적으로 조치해야 하는 상황이라면 번거롭다.

그러나 반복 조치가 필요한 상황이라면 API를 수동 호출하는 것보다 스케줄러나 이벤트
기반 자동 조치로 전환하는 편이 맞다. 수동 호출은 예외적인 상황을 다루는 경로이므로,
그쪽의 편의보다 안전성을 우선했다.

**재검토 조건**

- `dry_run=false` 한 값만으로 실제 조치가 실행된다. 영향 범위가 더 큰 작업이라면
  대상 이름을 다시 입력하게 하는 등 추가적인 확인 단계를 검토한다.
- 자동 조치를 상시 운영하는 구조로 바꾼다면 dry-run 기본값의 의미가 달라진다.
  그 경우 실행 전 승인 절차나 조치 이력 알림이 dry-run의 역할을 대신해야 한다.

### 점검은 API, 알림은 Lambda

**배경**

이 프로젝트에는 실행 방식이 다른 두 종류의 기능이 있다.

- **점검·조치** — 사람이 필요할 때 호출해 결과를 확인하고 판단한다
- **알림** — S3 설정 변경이 발생하면 사람의 개입 없이 즉시 동작한다

전자를 FastAPI 컨테이너로, 후자를 Lambda로 구현했다. 하나로 통일하지 않은 이유를
정리한다.

**검토한 선택지**

| 방식 | 장점 | 단점 |
|---|---|---|
| 전부 Lambda | 서버 관리 불필요, 사용량 기반 과금 | 실행 시간 제한, 로컬 개발·디버깅 번거로움, 상태 확인용 대화형 인터페이스 부재 |
| 전부 FastAPI | 개발·테스트 용이, Swagger 문서 자동 생성 | 이벤트 트리거를 받으려면 상시 기동 필요 |
| 용도별 분리 | 각 특성에 맞는 실행 모델 | 두 가지 배포·운영 방식을 함께 다뤄야 함 |

**결정**

점검·조치는 FastAPI, 알림은 Lambda로 분리했다.

**점검·조치를 API로 둔 이유** — 사람이 결과를 보고 판단하는 기능이다. Swagger UI로
엔드포인트를 탐색하고 파라미터를 조정하며 반복 호출할 수 있어야 한다. dry-run으로
결과를 확인한 뒤 실제 조치를 결정하는 흐름도 대화형 인터페이스에 맞는다.
로컬에서 컨테이너로 띄워 즉시 검증할 수 있다는 점도 개발 과정에서 컸다.

**알림을 Lambda로 둔 이유** — 이벤트가 언제 발생할지 알 수 없고, 발생 시점에만
동작하면 된다. 알림을 받기 위해 서버를 상시 기동하는 것은 비용과 관리 부담 때문에
비효율적이다. 처리 내용도 이벤트에서 필드를 추출해 Slack으로 전달하는 것뿐이라
실행 시간이 짧다.

**외부 의존성 제거**

Lambda는 표준 라이브러리 `urllib`만 사용한다. `requests`를 쓰면 코드는 짧아지지만
의존성을 함께 패키징해야 하고, Layer를 관리하거나 배포 패키지를 빌드하는 절차가
생긴다.

전송하는 요청이 Webhook POST 하나뿐이므로 표준 라이브러리로 충분하다고 판단했다.
`.py` 파일 하나를 Terraform이 그대로 배포한다.

**트레이드오프**

배포 방식이 두 가지가 된다. 점검 API는 컨테이너 이미지 빌드가, 알림은 Terraform
apply가 필요하다. 코드도 `main.py`와 `lambda/alert.py`로 나뉘어 있어 boto3 클라이언트
초기화 같은 부분이 중복된다.

기능 수가 적어 지금은 부담이 크지 않으나, 알림 로직이 복잡해지거나 점검 기능이
이벤트 기반으로 확장되면 이 방식을 다시 검토해야 한다.

**재검토 조건**

- 점검을 주기적으로 자동 실행해야 한다면 EventBridge Scheduler + Lambda가 적합하다.
  현재 구조에서는 API를 호출할 주체가 별도로 필요하다.
- 조치까지 이벤트 기반으로 자동화한다면 알림 Lambda가 조치 로직을 함께 수행하는
  형태가 자연스럽다. 다만 사람의 확인 없이 조치가 실행되므로, dry-run 기본값과
  같은 안전장치를 다른 방식으로 대체해야 한다.
- API를 상시 운영한다면 ECS/Fargate 배포와 인증 계층이 함께 필요하다.

### 로컬 클러스터 런타임 환경 — cgroup v2로의 전환
 
**배경**
 
기존 컴플라이언스 모니터를 EKS로 확장하기로 하면서, 매니페스트를 검증할 로컬
클러스터가 먼저 필요했다. EKS에서 바로 시작하면 매니페스트 문법 오류 하나를 잡는
데도 클러스터 기동 시간과 비용이 든다. 문법 단계의 시행착오는 로컬에서 털고 가는
편이 낫다고 판단해 kind를 선택했다.
 
첫 `kind create cluster`가 control-plane 시작 단계에서 실패했다. 인증서 생성,
kubeconfig 작성, static Pod 매니페스트 작성까지는 모두 성공했고 kubelet 시작 로그도
정상이었으나, 그 직후 API 서버(`172.19.0.2:6443`)에 대한 요청이 40초간
`connection refused`로 반복되다 중단됐다.
 
kubelet은 떴는데 kube-apiserver 컨테이너가 뜨지 못한 상태였다.
 
**원인 규명**
 
로그만으로는 원인이 특정되지 않아 후보를 세우고 각각을 측정으로 확인했다.
 
| 후보 | 확인 방법 | 결과 | 판정 |
|---|---|---|---|
| inotify 한도 초과 | `/proc/sys/fs/inotify/max_user_instances`, `max_user_watches` | 8192 / 1048576 | 배제 |
| 메모리 부족 | `free -h` | 31GB 중 25GB 여유 | 배제 |
| cgroup 버전 불일치 | `stat -fc %T /sys/fs/cgroup/` | `tmpfs` (= cgroup v1) | **원인** |
 
kind가 받아온 노드 이미지는 `kindest/node:v1.36.1`이었다. 실행 첫 줄에
`cgroup v1 is deprecated in Kubernetes` 경고가 출력됐는데, 이 버전대는 cgroup v2를
사실상 전제하므로 경고가 아니라 실패 원인이었다.
 
WSL2의 cgroup 버전은 WSL 커널이 결정한다. 즉 프로젝트 설정이 아니라 실행 환경의
문제였다.
 
**검토한 선택지**
 
| 방식 | 장점 | 단점 |
|---|---|---|
| WSL 커널 업데이트로 cgroup v2 전환 | 최신 노드 이미지를 그대로 사용. EKS 버전과 맞추기 쉬움 | WSL 재시작 필요, Docker Desktop 연동이 끊김 |
| 노드 이미지를 v1.31대로 낮춤 | 명령 한 줄로 즉시 우회 | 로컬과 EKS의 K8s 버전이 벌어짐. 버전 차이로 인한 동작 차이를 나중에 로컬에서 재현할 수 없음 |
 
**결정**
 
WSL 커널을 업데이트해 cgroup v2로 전환했다.
 
```
wsl --update
wsl --shutdown
stat -fc %T /sys/fs/cgroup/    # → cgroup2fs
```
 
이 프로젝트에서 로컬 클러스터의 역할은 "일단 뜨는 환경"이 아니라 **EKS에서의 동작을
미리 확인하는 환경**이다. 로컬과 EKS의 버전이 벌어지면 로컬에서 검증한 결과를
그대로 신뢰할 수 없게 되고, 로컬 클러스터를 두는 이유 자체가 약해진다.
 
우회 방식은 오늘의 1시간을 아끼는 대신 남은 기간 내내 "이 차이가 버전 때문인가"를
의심하게 만든다. 환경 문제는 발생 시점에 해결하는 편이 총비용이 낮다고 판단했다.
 
**트레이드오프**
 
`wsl --shutdown`이 Docker Desktop의 WSL 백엔드까지 함께 내린다. 재시작 후 WSL 안에서
`docker` 명령을 찾지 못하는 상태가 되어, Docker Desktop 실행과 WSL Integration 재확인이
추가로 필요했다.
 
원인 자체와는 무관한 부작용이지만, 조치 직후 나타나는 증상이라 별개의 장애로 오인하기
쉽다. 기록해 둔다.
 
**재검토 조건**
 
- EKS 클러스터 버전을 정할 때, 로컬 kind의 노드 이미지 버전과 맞춘다.
  둘이 벌어지면 로컬 검증 결과의 신뢰도가 떨어진다.
- NetworkPolicy 검증에는 기본 CNI가 아닌 Calico가 필요하다. 그 시점에
  별도 kind 클러스터를 구성해야 하므로, 노드 이미지 버전 관리 지점이 하나 더 생긴다.
- 다른 환경(다른 PC, CI)에서 클러스터를 만들 일이 생기면 cgroup 버전이 다시
  변수가 된다. kind 설정을 파일로 고정하는 방식을 검토한다.

### EKS + ArgoCD 완전 자동 배포를 보류한 이유

**배경**

kind 환경에서는 ArgoCD Application(`argocd/s3-monitor-app.yaml`)을 한 번
등록하는 것만으로 완전 자동 배포가 성립한다. `values-kind.yaml`이 계정
식별 정보를 전혀 포함하지 않아 그대로 Git에 커밋되어 있기 때문이다.
같은 방식을 EKS에도 적용하려 했으나, `values-eks.yaml`(ECR 이미지 경로,
IRSA Role ARN 등 AWS 계정 ID를 포함)은 이 프로젝트가 지켜온 원칙에
따라 `.gitignore` 처리되어 있어, ArgoCD가 Git에서 이 값을 읽을 방법이
없었다.

**검토한 선택지**

| 방식 | 문제 |
|---|---|
| `values-eks.yaml`을 그냥 커밋 | 계정 ID가 공개 저장소에 영구 노출. 이 프로젝트가 지켜온 원칙과 정면으로 배치 |
| ArgoCD `helm.parameters`에 값 직접 지정 | Application YAML도 Git에 커밋되는 파일이라 동일한 문제가 위치만 바뀌어 재발 |
| External Secrets Operator(ESO) 도입 | 실제로 IRSA Trust Policy까지 설계해 검증했으나, 근본적으로 다른 계층의 도구임이 드러남(아래 참고) |

**ESO가 이 문제에 맞지 않는 이유**

ESO는 AWS Secrets Manager의 값을 K8s Secret으로 동기화해, **애플리케이션이
런타임에 참조하는 시크릿**(API 키, DB 비밀번호 등)을 Git 밖에서 주입하는
도구다. 그런데 우리가 감추려는 값(`image`, `serviceAccountRoleArn`)은
**Pod가 뜨기 전에 매니페스트 구조 자체를 구성해야 하는 값**이다. 어떤
이미지를 pull할지, ServiceAccount에 어떤 annotation을 붙일지는 컨테이너가
실행되기 전에 이미 정해져 있어야 하므로, 런타임에 참조하는 Secret으로
대체할 수 없다. 인증(Trust Policy, IRSA Role)까지 실제로 만들어보고 나서야
이 구조적 한계가 명확해졌다 — 도구 이름만으로는 알기 어려웠던 지점이다.

**실무 사례와의 비교**

AWS 계정 ID 자체는 실무에서 대개 "비밀"로 취급되지 않는다. private
저장소가 기본이고, API 응답이나 CloudTrail 로그 등에 어차피 노출되기
때문이다. public 저장소에서 이 문제를 실제로 겪는 경우, 흔히 쓰는
해법은 CI/CD 파이프라인의 Secrets 저장소에서 배포 직전에 값을 주입하는
방식이다. 이는 **파이프라인이라는 별도 인프라가 이미 갖춰져 있다는
전제** 위에서 저비용으로 가능한 해법이며, 이 프로젝트에는 그 전제
자체가 없다.

**결정**

이 프로젝트 규모(개인 포트폴리오, public 저장소, 별도 CI/CD 파이프라인
없음)에서는 시크릿 관리 인프라를 새로 도입하는 비용이 얻는 이득보다
크다고 판단했다.

- **kind**: ArgoCD가 Git만으로 완전 자동 배포(drift 감지, selfHeal 포함
  검증 완료)
- **EKS**: Terraform으로 인프라 프로비저닝은 완전 자동화하되, 애플리케이션
  배포의 마지막 단계(`helm install`)는 수동 실행으로 남긴다. 계정 ID가
  필요한 `values-eks.yaml`은 로컬에만 유지하고, `values-eks.yaml.example`로
  형식만 공유한다(`k8s/overlays/eks/patch-*.yaml`과 동일한 패턴).

이는 몰라서 못 한 제약이 아니라, 세 가지 해법(직접 커밋, ArgoCD
parameters, ESO)을 실제로 검토·일부는 구현까지 해보고 비용 대비 효과를
따져 내린 판단이다.

**재검토 조건**

- CI/CD 파이프라인(GitHub Actions 등)을 도입하게 되면, 그 파이프라인의
  Secrets 저장소에서 배포 시점에 값을 주입하는 방식으로 EKS도 완전
  자동화할 수 있다.
- 여러 사람이 이 저장소에 기여하는 상황이 되면, private 저장소 전환이나
  Sealed Secrets 도입을 재검토한다 — 지금은 혼자 운영하는 로컬 파일
  관리로 충분하지만, 협업 환경에서는 "로컬에만 있는 값"이라는 전제가
  깨진다.

### Egress 정책을 아직 적용하지 않은 이유

**배경**

보안 기준선 점검 항목 7개 중 6개는 실제 구현·검증까지 마쳤으나
(RBAC, IRSA, securityContext 4종), Egress 정책만 계속 뒤로 밀렸다.
NetworkPolicy를 다룬 적은 있지만 Ingress(들어오는 트래픽) 방향만
설정했고, Egress(나가는 트래픽)는 명시적으로 보류한 적 없이 로드맵
우선순위에서 자연스럽게 밀렸다.

**설계해본 결과 — 표준 NetworkPolicy의 한계**

`default-deny-egress` 후 예외를 뚫는 구조 자체는 이미 적용한 Ingress
정책과 대칭적이라 어렵지 않다. DNS(CoreDNS) 예외는 네임스페이스·
Pod selector로 명확하게 좁힐 수 있다.

문제는 AWS API(S3, IAM, STS, CloudTrail) 예외다. 표준 K8s
NetworkPolicy는 클러스터 밖 트래픽을 **IP CIDR 블록**으로만
제한할 수 있고, 도메인 이름 기반 필터링을 지원하지 않는다. AWS가
`ip-ranges.json`으로 서비스별 IP 대역을 공개하긴 하지만, 이 대역은
AWS가 수시로 변경하므로 하드코딩하면 예고 없이 앱이 막힐 위험이
있다.

**실무 사례 조사**

이 문제를 표준 NetworkPolicy만으로 푸는 경우는 실무에서도 흔치 않다.
일반적인 해법은 계층을 분리하는 것이다.

- **VPC Endpoint** (Gateway: S3, Interface: STS/IAM/CloudTrail) — AWS API
  트래픽을 애초에 인터넷(NAT Gateway)으로 내보내지 않고 VPC 내부에서
  AWS 백본으로 직접 연결한다. 이러면 IP 대역 변동 문제 자체가 사라지고,
  Security Group으로 간단히 통제 가능해진다.
- **NetworkPolicy는 최후 방어선으로 축소** — VPC Endpoint로 경로가
  좁혀진 상태에서, "DNS + Endpoint로만 나가게" 허용하면 되므로
  전체 공인 IP 대역을 몰라도 된다.
- 더 정교한 FQDN 기반 필터링이 필요하면 Cilium 등 별도 CNI나 Istio
  같은 서비스 메시를 쓰는 경우가 많다 — 지금 쓰는 CNI(Calico OSS)의
  기본 기능 밖이다.

**결정**

VPC Endpoint 추가 자체는 Terraform 리소스 몇 개(Gateway Endpoint 1개,
Interface Endpoint 3개, Security Group 1개) 수준으로 규모가 크지
않다는 것까지 확인했다. 다만 이미 보안기준선 7개 중 6개를 실제
구현·검증까지 마친 상태에서, 남은 1개를 구현하는 것의 한계효용보다
**"어떻게 접근해야 하는지, 왜 지금 당장 하지 않았는지"를 정확히
기록해두는 것**이 이 시점에는 더 유효하다고 판단해 구현은 보류한다.

**재검토 조건**

- CSPM 확장(IAM Resource 스코핑과 함께)이나 별도 세션에서 VPC
  Endpoint(S3, STS, IAM, CloudTrail) + NetworkPolicy egress 예외를
  함께 구현한다.
- 이 프로젝트가 실제 프로덕션 트래픽을 받는 시점이 온다면, Egress
  통제 없이 컨테이너가 임의로 외부와 통신 가능한 상태는 우선순위를
  올려 즉시 해소해야 한다.
